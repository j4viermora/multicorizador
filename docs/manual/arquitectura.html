Arquitectura técnica

Stack, base de datos, namespaces, background jobs e integración con aseguradoras.

Stack tecnológico

Backend

  • Rails 8 — módulo Ruka
  • MariaDB — dev/test en Docker, prod vía APP_DATABASE_URL
  • Solid Queue — jobs en la misma DB
  • Devise — autenticación
  • acts_as_tenant — multi-tenancy

Frontend

  • Hotwire — Turbo + Stimulus
  • TailwindCSS 4 — sin Node
  • Flowbite — componentes UI
  • Tabler Icons — iconografía
  • simple_form — formularios

Infra

  • Dokploy — deploy (no Kamal)
  • Cloudflare R2 — storage (AWS_* vars)
  • Resend — email producción
  • Puma + Solid Queue — SOLID_QUEUE_IN_PUMA=true

Multi-tenancy

Con tenant (acts_as_tenant :company)

Quote, QuoteResult, Policy, Traveler, Link

Globales (sin tenant)

Provider, InsurancePlan, Company. Super admin opera con ActsAsTenant.current_tenant = nil.

Los background jobs no tienen contexto HTTP. Patrón: ActsAsTenant.without_tenant { Quote.find } → ActsAsTenant.with_tenant(quote.company) { ... }.

Modelo de datos — entidades clave

ModeloPropósitoCampos importantes
Quote Búsqueda de seguro de un viaje status, origin/destination, fechas, public_token, created_by
QuoteResult Respuesta de un aliado (un plan) external_quote_id, price, raw_response, status
Policy Póliza emitida (venta cerrada) policy_number, sold_via, premium, fechas, webhook_payload
Traveler Datos del viajero / cliente nombre, documento, email, birth_date
Provider Aliado aseguradora (config global) slug, status, config JSON
Link URL compartible con token token, expires_at, purpose
Columnas JSON en MariaDB requieren attribute :campo, :json en el modelo. Los fixtures deben usar strings JSON, no hashes YAML.

Concurrencia y pool de DB

config/queue.yml corre 3 threads. El pool en database.yml incluye +5 extra para workers + dispatcher + supervisor de Solid Queue. Si subís threads, subí el pool proporcionalmente.
